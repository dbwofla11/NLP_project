# 아이디어 시장검증 워크플로

## 목적

아이디어마다 다음을 시장 근거로 검증하고, 검증 결과와 남은 불확실성을 Notion에 일관되게 기록한다.

1. 문제 상황이 누구에게, 언제, 어떤 손실로 일어나는지 구체적인지
2. 그 문제가 실제 시장에서 반복적으로 발생하는지
3. 기존 해결 방식과 경쟁 서비스가 무엇인지
4. 아이디어가 기존 대안과 비교해 검증할 만한 차별 가설을 갖는지

이 과정은 아이디어의 성공을 단정하는 절차가 아니다. **확인된 사실, 합리적 추론, 아직 검증되지 않은 가설을 분리**하여 다음 현장 검증을 설계하는 절차다.

## 대상 선정과 상태 관리

- Notion 데이터베이스에서 `분석상태`가 `시작 전` 또는 `진행 중`인 행을 조회한다.
- 이미 `완료`인 항목도 별도 요청이 있으면 동일하게 검증한다. 기존 결과를 전제하지 말고 원 페이지와 하위 페이지를 다시 읽는다.
- 검증용 하위 페이지와 속성이 모두 기록되고 확인된 뒤에만 `분석상태`를 `완료`로 바꾼다.
- 검증 대상이 없으면 그 사실을 명확히 알린다.

## 반복 검증 루프

각 아이디어에 아래 1~5 단계를 수행한다. 근거가 약하거나 과장된 주장이 발견되면 해당 단계로 되돌아가 보완한다.

### 1. 원 아이디어 페이지 읽기

다음 요소를 추출한다.

- 한 줄 정의와 목표 고객
- 사용 맥락: 언제 어떤 일을 하는가
- 현재 해결 방식과 불편
- 주장하는 솔루션·MVP 범위
- 기존 점수, 한계점, 출처, 하위 페이지

페이지에 없는 내용을 사실처럼 채우지 않는다. 누락은 이후 `부족한 점`으로 남긴다.

### 2. 문제 상황 구체성 검증

문제 서술을 다음 다섯 요소로 분해한다.

| 요소 | 확인 질문 |
| --- | --- |
| 고객 | 누가 겪는가? 한 집단으로 좁혀졌는가? |
| 상황·계기 | 어떤 업무·사건·시점에 발생하는가? |
| 과업 | 사용자가 지금 무엇을 하려 하는가? |
| 손실 | 시간, 비용, 오류, 기회손실 중 무엇이 생기는가? |
| 기존 대안 | 스프레드시트, 검색, 전문가, 경쟁 제품 등으로 어떻게 해결하는가? |

판정 기준은 다음과 같다.

- **충족:** 다섯 요소가 특정 사용자와 실제 업무 흐름에 연결되고, 손실을 확인할 근거가 있다.
- **부분 충족:** 대상·과업은 있으나 빈도, 시간, 비용, 기존 대안의 한계 중 일부가 비어 있다.
- **미충족:** 막연한 불편 또는 기술 기능만 있고 사용자·상황·손실을 식별할 수 없다.

### 3. 반복 발생성 검증

반복성은 ‘그럴 것 같다’가 아니라 업무가 실제로 되풀이되는 시장 신호로 판단한다.

우선순위가 높은 근거는 다음과 같다.

1. 정부·공공기관 통계, 공식 공고, 법령, 산업협회 자료
2. 원시 데이터가 있는 연구·학술 논문·공식 제품 문서
3. 신뢰 가능한 시장 조사 및 공개 기업 자료
4. 경쟁 제품의 기능·요금·지원 흐름
5. 사용자 후기·커뮤니티 글: 문제 탐색용으로만 사용하며 시장 규모의 근거로 일반화하지 않음

다음 세 가지를 구분해 기록한다.

- **업무의 발생:** 시장조사, 신고, 계약 검토처럼 해당 업무 자체가 존재하는가
- **반복 주기:** 동일 사용자가 월별·공고별·문서 수정별로 다시 수행하는가
- **제안 기능의 반복성:** 예를 들어 ‘출처 재검증’처럼 세부 기능이 실제로 반복 사용되는가

공개 통계가 업무 발생만 보여 준다면 반복성은 `부분 충족`으로 판단한다. 제품 세부 기능의 사용 빈도는 인터뷰·파일럿 전까지 확정하지 않는다.

### 4. 솔루션·기존 방식·경쟁 대안 조사

조사 범위는 직접 경쟁사만으로 제한하지 않는다.

- 직접 경쟁: 같은 고객에게 비슷한 결과물을 제공하는 서비스
- 인접 경쟁: 일부 문제를 해결하는 범용 도구·플랫폼
- 비제품 대안: 검색, 수작업, 전문가·컨설팅, 커뮤니티

각 대안에 대해 `대상 고객`, `핵심 기능`, `근거·검증 기능`, `가격 또는 이용 방식`, `제안 아이디어와 겹치는 부분`을 기록한다.

경쟁사의 마케팅 문구는 기능 존재의 보조 근거일 뿐 성과·시장 규모의 독립 근거가 아니다. 특히 “AI가 시간을 절약한다”, “많은 사용자가 선택했다” 같은 표현은 해당 회사의 주장임을 표시한다.

### 5. 비판적 재검토

조사 결과를 아래 질문으로 다시 반박한다.

- 통계의 모집단이 실제 목표 고객과 일치하는가?
- 자료가 현재 시점에도 유효한가?
- 업무 발생을 제품 수요 또는 지불의사로 과장하지 않았는가?
- 경쟁 제품이 이미 제공하는 기능을 차별점처럼 말하지 않았는가?
- ‘있을 법한 기능’과 실제 사용자 행동을 혼동하지 않았는가?
- 출처가 주장 전체를 직접 뒷받침하는가?

근거가 부족하면 결론을 낮추고, 다음 검증 항목에 구체적인 인터뷰 또는 파일럿을 추가한다. 가능한 경우 독립된 관점의 검토자 또는 서브에이전트에게 이 질문 목록으로 비판 검토를 맡기고, 지적을 반영한 뒤 다시 점검한다.

## Notion 기록 형식

각 아이디어 페이지 아래에 `문제 상황·반복성 시장 검증`이라는 하위 페이지를 만든다. 다음 구조를 기본으로 쓴다.

```markdown
검증 범위: 시장 관점에서 문제 상황의 구체성과 반복 발생성만 검증함.

# 검증 결론
| 질문 | 판정 | 시장 근거와 해석 |
| --- | --- | --- |
| 문제 상황이 구체적인가? | 충족/부분 충족/미충족 | ... |
| 문제가 반복되는가? | 충족/부분 충족/미충족 | ... |

# 1. 문제 상황의 구체성 검증
## 이미 구체화된 요소
- 고객:
- 상황·과업:
- 손실:
- 기존 대안:

## 부족한 구체성
- ...

# 2. 반복 발생성의 시장 근거
- 사실 + 출처 + 그 사실이 뒷받침하는 범위
- 사실 + 출처 + 해석의 한계

## 반복성 판정의 한계
- ...

# 3. 반드시 보완할 현장 검증
1. 인터뷰 대상·질문·표본 수
2. 파일럿 과업·비교 기준
3. 사전에 정한 성공/실패 기준

# 최종 판단
- 문제상황 구체화 여부:
- 문제 상황의 반복적 발생 여부:
```

### 작성 원칙

- 출처 URL을 각 주장 가까이에 링크한다.
- 출처의 의미를 넘겨 일반화하지 않는다. 예: 전국 창업자 통계는 특정 전공의 예비창업팀 수요를 직접 증명하지 않는다.
- 공급자 자료는 `공급자 측 신호`로 표기한다.
- 검증 범위 밖인 구현 난이도·가격·시장규모는 이 하위 페이지의 결론으로 단정하지 않는다.
- 부족한 점은 “추가 조사 필요”로 끝내지 않고, 누구에게 무엇을 어떤 기준으로 확인할지 쓴다.

## 데이터베이스 속성 반영

하위 페이지 작성 후 다음 속성을 짧고 검증 가능한 문장으로 업데이트한다.

| 속성 | 입력 방식 |
| --- | --- |
| `문제상황 구체화 여부` | `충족`, `부분 충족`, `미충족` 중 하나와 핵심 근거·부족점을 한 문장으로 기록 |
| `문제 상황의 반복적 발생 여부` | 같은 방식으로 업무 발생과 기능별 반복성을 분리해 기록 |
| `한계점` | 차별화·표본·데이터·기술 제약 중 가장 중요한 미해결 위험을 짧게 기록 |
| `전체적인 주제 적합도` | 모든 검증이 끝난 뒤에만 상·중·하 평가 |
| `시장경쟁력 & 차별성` | 경쟁 대안과 현장 검증 결과를 반영해 상·중·하 평가 |
| `구현 난이도 및 NLP사용여부` | MVP 범위와 NLP의 핵심성 기준으로 상·중·하 평가 |
| `분석상태` | 하위 페이지·속성·검증 확인이 끝난 뒤 `완료` |

## 완료 전 체크리스트

- [ ] 원 아이디어 페이지와 기존 하위 페이지를 읽었다.
- [ ] 공신력 있는 시장 근거를 최소 하나 이상 사용했다.
- [ ] 직접 경쟁·인접 경쟁·비제품 대안을 구분했다.
- [ ] 문제 구체성과 반복성을 별도로 판정했다.
- [ ] 확인 사실, 추론, 미검증 가설을 구분했다.
- [ ] 근거 부족·누락·과장을 비판적으로 재검토했다.
- [ ] 부족한 점을 인터뷰 또는 파일럿의 측정 가능한 다음 단계로 바꿨다.
- [ ] Notion 하위 페이지, 데이터베이스 속성, 상태를 모두 다시 확인했다.
